## 工具设计规范

工具定义系统分为两层，职责分离：

### 工具定义层

每个工具是一个包含工具具体实现的「类」：工具名称与各参数名称是固定值（如 `"Shell"`、`"path"`），工具描述与各参数描述则均为翻译键（如 `"tool.shell.desc"`、`"tool.read.desc"`）。

- **数据**：工具名称与各参数名称为固定值，工具描述与各参数描述均为翻译键。
- `ToolParam` 描述一个参数：`name`（参数名）、`kind`（类型提示）、`description`（描述）、`required`（是否必需）、`semantic`（语义分类，见下）。
- 每个参数的 `semantic` 字段标记该值的用途，供审核层泛化判断：
  | 语义 | 用途 | 审核含义 |
  |------|------|----------|
  | `None` | 普通参数 | 无需特殊检查 |
  | `PathRead` | 读取文件/目录路径 | 需做工作区边界检查（超出工作区则弹审核） |
  | `PathWrite` | 写入文件路径 | 需做工作区边界检查（超出工作区则弹审核）；非接受编辑模式=>需要审核 |
  | `PathExec` | 命令执行目录路径 | 一般始终审查 |
  | `Command` | Shell 命令 | 需匹配白名单（非白名单命令弹审核） |
  | `Content` | 涉及写入/编辑操作的、与工作区内容强相关的字符串 | 隐私保护由独立的 sanitize/restore 管线处理，审核层始终放行 |
- 所有内置工具通过 `all_tools()` 收集，是"哪些工具存在"的唯一真相来源。

### 解析器层

每种调用格式（XML、JSON 代码块等）实现 `ToolCallFormatParser` trait：

```rust
pub trait ToolCallFormatParser: Send + Sync {
    fn format_name(&self) -> &'static str;
    fn try_parse(&self, input: &str) -> Result<Vec<ParsedToolCall>, ParseError>;
    fn tool_call_template(&self, tool: &dyn ToolDef) -> String;
}
```

- **解析与渲染对称设计**：`try_parse()` 将输入文本转为结构化调用，`tool_call_template()` 将工具定义渲染为该格式的标准调用模板。
- **`FormatRegistry`** 管理所有注册的解析器，支持 `AutoDetect`（自动探测）和 `Fixed(format)`（固定格式）模式，线程安全（`RwLock`）。

### 核心原则

1. **工具定义不感知格式**：添加新调用格式只需实现一个 trait 并注册，无需修改任何工具。
2. **每个格式自包含**：解析和模板渲染在同一 trait 中，格式的完整知识只存在于一个地方。
3. **工具是数据，解析器是行为**：这种分离使系统可扩展——新增格式不影响现有工具，新增工具自动被所有格式支持。
